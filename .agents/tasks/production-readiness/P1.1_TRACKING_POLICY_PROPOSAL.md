# Public Tracking Scoped Access Policy Proposal

## Background & Current Gap
Codex has rejected the previous implementation of public tracking access (which relied solely on limiting the response payload via `OrderTrackingDTO`) because it leaves the system vulnerable to **Order Enumeration** (e.g., iterating through `ORD-001`, `ORD-002`, or brute-forcing phone numbers). The acceptance criteria strictly mandate "scoped public tracking access."

## Assessment of Current Architecture
Currently, there is no separate "customer portal auth token" or JWT issued to customers. The frontend component `ShopFloorTracker.tsx` is built as an unauthenticated UI where users simply type in their "Order Number/ID". 
Changing the backend to require an authentication token for tracking would break the existing customer tracking UI. 

## Bounded Scoped Policy Options

### Option A: Enforce Exact UUID Tracking Links (Recommended)
Instead of searching by the short `OrderNo` (e.g., `ORD-001`) or `CustomerPhone`, the public tracker should only accept the order's internal UUID (`order.ID`) or a dedicated high-entropy `TrackingCode`.
*   **Backend Changes (`orders/handlers.go`)**: 
    - `HandleTrackOrderQuery`: Reject queries that are shorter than 16 characters or do not match a UUID format. Remove phone-number lookup fallback.
*   **Frontend Changes (`ShopFloorTracker.tsx`)**:
    - Update placeholder text from "Search Order Number" to "Enter Tracking Link / Tracking ID".
*   **Impact**: Breaks backward compatibility for customers currently tracking via short `ORD-XXXX` codes, but definitively solves enumeration.

### Option B: Rate Limiting + Phone Number Verification Challenge
Require customers to provide BOTH the `OrderNo` AND their `CustomerPhone` to access the tracker.
*   **Backend Changes (`orders/handlers.go`)**: 
    - `HandleTrackOrderQuery`: Accept `q` (OrderNo) and a new query parameter `phone`. Validate that `order.CustomerPhone == phone`. Apply a rate limit of 10 requests/minute per IP to prevent brute-forcing the phone number.
*   **Frontend Changes (`ShopFloorTracker.tsx`)**:
    - Add a second input field for "Phone Number" in the tracking form.
    - Update `apiFetch` in `ShopFloorTracker.tsx` to append `&phone=xxx` to the URL.
*   **Impact**: Maintains use of friendly `ORD-XXXX` codes while requiring secondary PII knowledge to unlock the DTO.

## Proposed Action Plan
Unless Option B is explicitly preferred by the product owner, we recommend proceeding with **Option A**. The implementation will target the exact files listed above to seamlessly close the enumeration gap without introducing new authentication mechanisms or customer accounts.
